# KTS Settlement — Session-bound narrow receipt read (DESIGN CANDIDATE; NO RELEASE)

## Why the currently proven behavior is BLOCKED

Fresh synthetic PostgreSQL16 with a separately authenticated ledger LOGIN demonstrated that a caller who controls that SQL connection can change `kts.workspace_id` from `group_a` to `group_b` and SELECT another workspace receipt. This is a **successful threat diagnostic, failed stand-alone tenant isolation**. No source evidence proves injection or credential compromise in an actual deployment. Source-bound successful observation and rollback acknowledgement: commit `2ab3e56be00956ce699fb6c8741f90cf6d7ec3cf`; qualification SHA256 `E54F84F4A130AF76BC99D4EB545D375B00CAB600E911D06123444BCC6D2FB5A4` reported by Codex Windows; original Windows receipt bytes not independently materialized in this GitHub review.

Today, `lookupRecoveryReceipts` in `team-settlement/postgres-ledger-repository.cjs` does direct `SELECT` from `kts_team.idempotency_receipts` and `kts_team.scope_events` under a ledger LOGIN with direct table/column grants. It also verifies the trusted HTTP actor and active membership; the HTTP workflow then verifies the session again. Those controls reduce risk **but do not make a compromised SQL connection tenant-safe**. `team-settlement/team-composition.cjs` correctly blocks real money writes.

## Review-only DDL candidate

`team-settlement/candidate/session-bound-receipt-read-v1.sql` is a **non-deployed, opt-out/default-off** proposal. It MUST NOT be included in canonical migrations or run on a live/reused PostgreSQL cluster. There is no GRANT to an application role, no backend route wiring and no write activation.

The candidate accepts a short-lived, domain-separated HMAC proof tied to the session hash identifier, tenant, strict ordered unique request keys, nonce and expiry. A **non-login, non-BYPASSRLS SECURITY DEFINER** function validates active `kts_auth.sessions`, matches the signed tenant to session.workspace_id, applies `set_config('kts.workspace_id', session.workspace_id, true)` only **after** signature validation, verifies nonrevoked membership and enabled identity, requires admin/operator, and returns only actor-owned requested receipt/event fields. It has `SET search_path=pg_catalog` and `REVOKE ALL ... FROM PUBLIC`, with no runtime EXECUTE grant. A separate reviewed `kts_receipt_read_owner` would need minimal internal SELECT rights and function-creation authority only inside a fresh, synthetic admission. Creation and crypto owner provenance are **NOT_VERIFIED**.

This read function is NOT a blanket proof of transaction/session authorization: it does not lock rows and can be replayed within its 30-second proof validity; a concurrent revoke can occur between its snapshot and HTTP response, so post-check/race tests are mandatory. The existing HTTP flow performs a second session verification, but that separate transaction alone does not establish atomic revocation and receipt-read ordering. A compromised bearer token, HMAC proof capture, owner misconfiguration, or logging leak remains relevant. No proof material may appear in GitHub receipts.

**Backend origin is not proven by this HMAC.** The HMAC key is `session_hash`, which is SHA-256 of the bearer token. Anyone holding the bearer can compute that key and construct valid envelopes for that session. A protected database connection and server-side authorization remain essential; a claim that a proof can only be generated by the backend is false. A separately managed backend-only secret or a different reviewed authority boundary is required if backend origin must be established. This observation does not by itself show cross-tenant access or a leaked bearer. The owner precheck also rejects membership in any other role, but it does not replace a complete effective-privilege and default-ACL audit.

## Mandatory migration and qualification gates BEFORE any deployment

1. **No direct data access for runtime Ledger:** revoke SELECT on `idempotency_receipts`, `scope_events` and sensitive membership/identity table/column paths as needed from the untrusted LOGIN; verify effective inherited/direct/PUBLIC/column privileges using a real authenticated session. Deny schema CREATE, BYPASSRLS, raw mutation EXECUTE and membership grants; keep Auth and Ledger logins distinct. An attempted direct SELECT after forged tenant GUC must fail with insufficient_privilege regardless of tenant. The candidate alone does **not** close the current vulnerability while existing direct SELECT remains.
2. **Read function boundary:** prove only reviewed Ledger LOGIN may EXECUTE; the current user and default PUBLIC may not. Check `pg_proc.proowner`, `pg_proc.proacl`, `pg_default_acl`, role memberships, crypto extension owner `kts_crypto.hmac` and every referenced schema function. Non-owner and no BYPASSRLS is required; FORCE RLS and explicit policies must remain intact.
3. **Source-to-SQL proof parity:** implement separately reviewed backend-only signer and narrow repository adapter, each disabled by default. Recompute exactly the same ordered HMAC envelope and verify nonce/expiry/keys/cross-workspace/revoked session. A replayed proof must not authorize a broader key set or tenant. Test missing receipt `UNKNOWN` with `auto_retry:false`, strict digest/actor/event/revision equality and no additional event/receipt. No browser-provided proof or raw session hash accepted.
4. **Real PostgreSQL16 synthetic QA:** run on a unique, SHA-bound, supervised C:-only disposable PGDATA using only approved offline dependencies. Positive valid proof works; GUC forgery, invalid/expired/replayed-to-different-keys proof, wrong role, wrong session tenant, revoked session, revoked membership, changed role, disabled identity, tampered receipt and concurrent revocation all fail closed. Verify read-only transaction, ROLLBACK/COMMIT tags, terminal PID and port, error retention, source hashes. DO NOT rerun unrelated PASS QA on unchanged SHA.
5. **Operational readiness:** independently review actual proposed deployment configuration, Auth/Ledger credential exposure, SQL injection surface, error/audit/proxy/backup logging, parameter and HMAC proof masking/rotation/retention, client encryption and browser/Android crash recovery. Run the approved business-money HIOSKT oracle, end-user review and explicit independent security signoff. Existing `WRITE_BLOCK` must remain ENABLED until **all** release gates pass.

## Verdict

This is a **technical design artifact**, not a security-approved read path. The function is intentionally unreferenced by any running component. Passing static tests or future DDL compilation is **not** evidence of operational tenant isolation. Cross-surface impact: SQL design only; no Router, Unified, Desktop, Android/PWA, customer settlement money logic or Tách Ngang changes.
